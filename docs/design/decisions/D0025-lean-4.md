## Question

In which proof assistant is the core mechanized ([D0024](D0024-mechanize-the-core.md))? The choice decides the daily
experience of the mechanization work (automation, error messages, editor support, release churn), whether the
definitions can run ([D0027](D0027-executable-reference.md)), and what separation-logic machinery is available if
the revisit trigger of [D0021](D0021-formal-target-sequential-language.md) fires.

## Options considered

Every candidate is shown on the same sample: the application rule with its latent effect `φ`, and the
effect-soundness theorem for a small calculus. Lean 4 and Rocq were piloted; the Isabelle and Agda samples were not
run ([R0004](../research/R0004-formalization-prior-art-and-pilots.md)).

### A. Lean 4

```lean
inductive HasType : List Ty → Expr → Ty → Eff → Prop where
  | app {Γ f x a b φ φ₁ φ₂} :
      HasType Γ f (.arrow a φ b) φ₁ → HasType Γ x a φ₂ →
      HasType Γ (.app f x) b ((φ₁.join φ₂).join φ)
  | sub {Γ e τ φ φ'} : HasType Γ e τ φ → φ.le φ' → HasType Γ e τ φ'
theorem effect_soundness {e v τ t} (ht : HasType [] e τ .pure) (he : Eval e v t) :
    t = [] ∧ HasType [] v τ .pure
```

- **How it works:** a dependently typed programming language that is also a prover; proofs are tactic scripts;
  definitions compile and run.
- **Pilot:** 182 lines, checked in under a second. Errors stay local and name the failing case; one pitfall
  (method-call notation feeding the wrong argument) suggests a style rule.
- **Easy:** editor support through the language server; strong automation; runnable definitions.
- **Hard:** frequent releases with occasional breaking changes; the Iris port is maturing but behind Rocq's
  (verified, R0004); no mature de Bruijn library.

### B. Rocq

```coq
Inductive has_type : list ty -> expr -> ty -> eff -> Prop :=
| T_App : forall G f x a b p p1 p2,
    has_type G f (TArrow a p b) p1 -> has_type G x a p2 ->
    has_type G (EApp f x) b (join (join p1 p2) p)
| T_Sub : forall G e T p p', has_type G e T p -> le p p' -> has_type G e T p'.
Theorem effect_soundness : forall e v T t,
  has_type [] e T Pure -> eval e v t -> t = [] /\ has_type [] v T Pure.
```

- **How it works:** a tactic-based prover on the Calculus of Inductive Constructions; programs are extracted to
  OCaml to run.
- **Pilot:** 171 lines, checked in under a second, written after the Lean proof had fixed the structure. Failing
  automation inside a bullet reported only an unfinished bullet, without the goal.
- **Easy:** the largest body of language-metatheory work (*Software Foundations*, CompCert, WasmCert, Iris); stable.
- **Hard:** terser errors; a lighter editor experience.

### C. Isabelle/HOL

```isabelle
inductive has_type :: "ty list ⇒ expr ⇒ ty ⇒ eff ⇒ bool" where
  T_App: "has_type G f (TArrow a p b) p1 ⟹ has_type G x a p2 ⟹
          has_type G (EApp f x) b (join (join p1 p2) p)"
| T_Sub: "has_type G e T p ⟹ le p p' ⟹ has_type G e T p'"
theorem effect_soundness:
  "has_type [] e T Pure ⟹ eval e v t ⟹ t = [] ∧ has_type [] v T Pure"
```

- **How it works:** classical higher-order logic; readable structured proofs; Sledgehammer calls external provers.
- **Easy:** the strongest automation; *Concrete Semantics*; the first WebAssembly mechanization (verified, R0004).
- **Hard:** a heavy dedicated editor; yearly releases; less mature separation-logic tooling for our purpose.

### D. Agda

```agda
data _⊢_⦂_!_ : Ctx → Expr → Ty → Eff → Set where
  ⊢app : Γ ⊢ f ⦂ (a ⇒[ φ ] b) ! φ₁ → Γ ⊢ x ⦂ a ! φ₂ → Γ ⊢ app f x ⦂ b ! (φ₁ ⊔ φ₂ ⊔ φ)
  ⊢sub : Γ ⊢ e ⦂ τ ! φ → φ ≤ φ′ → Γ ⊢ e ⦂ τ ! φ′
effect-sound : [] ⊢ e ⦂ τ ! pure → e ⇓ v ⊣ t → t ≡ [] × [] ⊢ v ⦂ τ ! pure
```

- **How it works:** proofs are programs written by pattern matching, filled in through interactive holes.
- **Easy:** close to the mathematics; *Programming Language Foundations in Agda*.
- **Hard:** weak automation; an Emacs-centered workflow; the smallest ecosystem for large developments.

| | Lean 4 | Rocq | Isabelle/HOL | Agda |
| --- | --- | --- | --- | --- |
| Piloted | yes | yes | no | no |
| Automation | strong | moderate | strongest | weak |
| Separation logic | Iris port maturing | Iris, mature | weaker | little |
| Definitions run | natively | by extraction | by code generation | via Haskell |
| Release churn | high (pin it) | low | yearly | moderate |

Recommendation at the time: **Lean 4, narrowly over Rocq**, because daily experience (editor, error messages) and
runnable definitions dominate a multi-year mechanization; Rocq was named the defensible choice for its textbook path
and mature Iris.

## Choice

**Lean 4.** The toolchain version is pinned in the mechanization's `lean-toolchain` file and changed only
deliberately, with the proofs re-checked in the same change.

## Rationale

The mechanization grows with every milestone, so the tool we work in daily matters most: Lean's editor support and
precise, case-named errors were clearly better in the pilot, and its definitions run directly, which the executable
reference ([D0027](D0027-executable-reference.md)) uses. Rocq's main advantage, a mature Iris, matters only if the
revisit trigger of D0021 fires, and the Lean port of Iris is progressing.

## Consequences

- **Release churn** is handled by pinning; toolchain bumps are their own changes.
- **A style rule** for the Lean sources avoids method-call notation on multi-argument syntax functions, which the
  pilot showed can silently supply the wrong argument.
- **T0006** may weigh the fact that Lean is also a programming language when choosing the host language.
- **If D0021's revisit trigger fires**, the state of separation logic in Lean is part of that revisit.
